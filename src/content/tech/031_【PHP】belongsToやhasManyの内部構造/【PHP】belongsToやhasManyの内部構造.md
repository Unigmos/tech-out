# 【PHP】belongsToやhasManyの内部構造

Laravelを始めたときに大体出てくる仕組みですが、改めて調べ直してみました。<br>

## そもそも何か

belongsToやhasManyは1対多の関係を示すペアのようなものです。<br>
よくある例えだと、ユーザーと投稿の関係で1人のユーザはたくさんの投稿を持てて、1つの投稿は必ず1人のユーザに所属しているといったイメージです。<br>
<br>
この関係をLaravelのModel側に明記しておくことで紐づけ先の情報が取得しやすくなり、オブジェクトとして扱いやすくなります。<br>
※これらはあくまでコード上でクエリ発行しやすくするだけで、DBの構成が変わったりするわけではないので、使い勝手は良いと思います。<br>

## どうやって紐づけ、取得しているの？

本題です。<br>
例に挙げた「ユーザーと投稿の関係」で細かいデータ取得する際はlaravelで以下のような記載になると思います。<br>

```php
$posts = Post::with('user')->get();

foreach ($posts as $post) {
    echo "タイトル: " . $post->title;
    echo "作成者: " . $post->user->name; 
}
```

ここでいう「$postにuserなんてプロパティないのにどうやってとってきているか」という部分について紹介したいと思います。<br>
<br>
結論としては、Model.phpの中に__getというマジックメソッドがあり、そこで呼び出しているようです。<br>
※発火条件は存在しないプロパティにアクセス時<br>
<br>
全部説明すると長くなるので一部省略しますがその先で呼ばれてるメソッドの中に以下のような記載があります。<br>

```php
return $this->isRelation($key) || $this->relationLoaded($key)
    ? $this->getRelationValue($key)
    : $this->throwMissingAttributeExceptionIfApplicable($key);
```

リレーションかどうかをチェックする処理があり、trueの場合にはクエリが発行されることで、紐づく情報を取得できるようです。<br>
※この処理の前にカラムやミューテタではないかや基底メソッド(save()等)でないかのチェックを挟みます。<br>

## N+1問題について

リレーションに関する題材に触れたので、N+1問題についても触れたいと思います。<br>
ザックリいうと、forループ等の中で都度クエリを発行するせいで、本来2回のクエリ発行でいいものをレコードが10000件あったら約10000件発行してしまいパフォーマンスが落ちるという問題です。<br>
<br>
特にLaravelのEloquentの様なORMで起こり、ORMが便利にSQLに変換してくれる一方で気づいたらパフォーマンスがガタ落ちしてたみたいな状況が起こりえてしまいます。<br>
もちろん回避策もあり、withメソッドを用いて事前に読み込みさせておくEager Loadという方法もLaravelにはあるので、その辺りも利活用できるといいのかなと思います。<br>

## 所感

他の処理含めリクエスト毎にこれらの処理をすべて捌いていると考えると、結構パフォーマンスも気になりますね、、<br>
普段vendor配下なんて見ないですが、また気になるところ出れば見てみようと思います。<br>
